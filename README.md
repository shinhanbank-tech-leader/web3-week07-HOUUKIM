## 1. 기존 은행 시스템 변경 방식

### 1.1 변경 프로세스 구조

기존 은행 시스템의 변경은 중앙화된 통제 하에 이루어진다. 기존 은행 시스템의 경우 변경 요건이 발생하면 요건 분석 → 개발 → 테스트(단위/통합/수용) → 운영 배포의 단계를 거친다. 배포는 주로 야간 배치 처리 완료 후 무중단 또는 점검 창구를 통해 진행되며, 문제 발생 시 즉각 롤백이 가능하다.

미들웨어 환경에서는 전문 포맷 변경 시 송수신 기관 양측의 동시 배포 혹은 버전 협의가 필요하며, 이를 은행 내부적으로 일정 조율하여 변경을 수행한다. 오류 발생 시 관리자 권한으로 즉각 수정 및 재배포가 가능하다는 점이 핵심 특징이다.

### 1.2 주요 특징

- **중앙집중식 통제**: 관리자 권한으로 언제든 코드 수정 및 롤백 가능
- **유연한 변경**: 긴급 패치, 핫픽스 등 신속한 대응 가능
- **신뢰 기반 구조**: 은행(운영자)을 신뢰하는 모델로 설계됨
- **버전 관리**: 형상관리 도구를 통한 변경 이력 추적
- **다운타임 위험**: 배포 과정에서 서비스 중단 가능성 존재

## 2. 스마트컨트랙트 업그레이드 방식

### 2.1 Immutable 특성과 업그레이드 필요성

스마트컨트랙트는 블록체인 네트워크에 한번 배포되면 코드 자체를 수정할 수 없다. 이는 코드를 신뢰의 근거로 삼는 블록체인의 핵심 철학에서 비롯된다. 그러나 실제 금융 서비스에서는 버그 수정, 기능 개선, 규제 대응 등의 이유로 변경이 불가피하다. 이 딜레마를 해결하기 위해 다양한 업그레이드 패턴이 등장하였다.

### 2.2 주요 업그레이드 패턴

**1 프록시 패턴**

사용자는 프록시 컨트랙트 주소를 통해 호출하고, 실제 로직은 구현 컨트랙트가 담당한다. 업그레이드 시 프록시가 가리키는 구현 컨트랙트 주소만 변경한다. EIP-1967 표준을 따르는 Transparent Proxy와 UUPS(Universal Upgradeable Proxy Standard) 방식이 대표적이다.

```
사용자 → [프록시 컨트랙트] --delegatecall→ [구현 컨트랙트 v1]
                                                       업그레이드
사용자 → [프록시 컨트랙트] --delegatecall→ [구현 컨트랙트 v2]
(주소 동일)
```

**2 데이터 분리 패턴**

로직 컨트랙트와 스토리지 컨트랙트를 분리하여, 로직만 새로 배포하고 데이터는 유지한다. 상태 변수 슬롯 충돌 위험이 없다는 장점이 있다.

**3 다이아몬드 패턴 (EIP-2535)**

하나의 프록시에 여러 구현 컨트랙트를 붙여 모듈 단위로 업그레이드한다. 대규모 복잡한 시스템에 적합하나 구조가 복잡하다.

### 3.3 프록시 패턴 동작 방식

핵심 메커니즘은 `delegatecall`이다. 프록시 컨트랙트는 구현 컨트랙트의 코드를 자신의 컨텍스트에서 실행한다. 로직은 구현 컨트랙트의 코드를 사용하되, 상태(스토리지)는 프록시 컨트랙트에 저장된다. 업그레이드 시 구현 컨트랙트 주소만 새 주소로 교체하면 사용자는 동일한 주소로 계속 호출하면서 변경된 로직을 적용받는다.

## 4. 비교 분석

### 4.1 핵심 차이점 비교

| 구분 | 기존 은행 시스템 | 스마트컨트랙트 |
|------|----------------|--------------|
| 신뢰 모델 | 기관(은행)을 신뢰 | 코드를 신뢰 |
| 변경 주체 | 관리자/운영팀 (중앙) | 거버넌스/다중서명 (탈중앙) |
| 롤백 가능 여부 | 즉각 롤백 가능 | 불가 (새 버전 재배포) |
| 변경 투명성 | 내부 감사 로그 | 블록체인 상 공개 기록 |
| 변경 속도 | 빠름 (수 시간 내) | 느림 (거버넌스 의결 필요) |
| 데이터 연속성 | DB 마이그레이션 용이 | 스토리지 슬롯 충돌 위험 |
| 보안 위험 | 내부자 위협 | 업그레이드 권한 탈취 |

### 4.2 거버넌스 측면 비교

기존 은행 시스템에서 변경 권한은 내부 결재 라인과 실무 협의체를 통해 통제된다. 반면 스마트컨트랙트의 업그레이드는 온체인 거버넌스 또는 멀티시그 방식으로 이루어진다.

은행 시스템에 적용한다면, 단일 기관이 로직을 단독으로 변경할 수 없고 사전에 합의된 거버넌스 구조를 통해서만 변경 가능한 형태가 된다. 이는 기관 간 신뢰를 제도가 아닌 코드로 보장한다는 점에서 기존 방식과 근본적인 차이가 있다.

### 4.3 실무 적용 시 고려사항

금융 시스템에 스마트컨트랙트를 도입할 때 업그레이드 관련하여 특히 주의해야 할 사항이 있다.

- **스토리지 레이아웃 충돌**: delegatecall 기반 프록시에서 상태 변수 순서가 변경되면 기존 데이터가 손상될 수 있어, 새 변수는 반드시 기존 변수 뒤에만 추가해야 한다.
- **타임락**: 금융 서비스에서 즉각적인 업그레이드는 악용 가능성이 있으므로, 업그레이드 실행 전 일정 기간의 지연 시간을 두어 이해관계자의 검토 및 대응 기회를 제공해야 한다.
- **감사 필수화**: 코드 변경 시마다 보안 감사를 수행하여 업그레이드로 인한 취약점 도입을 방지해야 한다.
- **긴급 중지 기능**: 취약점 발견 시 즉각 서비스를 중단할 수 있는 기능을 구현해두어야 하며, 이 권한 역시 멀티시그로 통제하는 것이 바람직하다.
- **온체인/오프체인 경계 명확화**: 어떤 로직이 왜 온체인인지, 왜 오프체인인지 모든 참여 기관이 납득할 수 있어야 한다. 이 경계가 불명확하면 신뢰 구조 자체가 흔들린다.

## 5. 결론

기존 은행 시스템과 스마트컨트랙트의 변경 방식은 단순히 기술적 차이를 넘어 신뢰의 근거를 어디에 두느냐의 철학적 차이에서 비롯된다. 기존 방식이 '기관에 대한 신뢰'를 기반으로 한다면, 스마트컨트랙트는 '코드에 대한 신뢰'를 바탕으로 동작한다.

그러나 현실의 금융 시스템에서 둘 중 하나를 택하는 것은 적절하지 않다고 생각한다. 은행 코어 원장은 규제 대응, 긴급 패치, 고객 데이터 처리 등 유연성이 필수적인 영역을 담당한다. 금융당국의 새 규정이 내려오면 타임락을 기다릴 여유가 없고, 롤백 불가 구조는 원장 운영의 현실과 맞지 않는다. 반면 기관 간 정산 규칙, 담보 비율 등 참여 기관 모두가 동의한 로직은 온체인으로 확정함으로써 단독 변경 불가라는 신뢰를 코드로 보장할 수 있다.

따라서 현실적인 구조는 하이브리드다. 코어 원장은 기존 방식으로 운영하되, 기관 간 합의가 필요한 규칙은 스마트컨트랙트로 확정하는 역할 분리가 필요하다. 다만 하이브리드 구조에서도 핵심 질문은 항상 동일하다. 이 로직을 모든 참여자가 신뢰할 수 있는가. 기술적으로 아무리 잘 설계해도 이 질문이 해결되지 않으면 도입의 의미가 없다.

신뢰를 유지하기 위해서는 세 가지가 함께 작동해야 한다. 첫째, 온체인 로직은 누구나 검증 가능하도록 소스와 감사 결과를 공개해야 한다(코드 투명성). 둘째, 업그레이드 권한이 특정 기관에 집중되지 않도록 멀티시그와 타임락으로 단독 변경을 구조적으로 차단해야 한다(거버넌스). 셋째, 온체인과 오프체인의 경계와 그 이유를 모든 참여 기관이 납득할 수 있어야 한다(경계 명확화).

결국 신뢰는 기술이 주는 것이 아니라 설계와 거버넌스가 만드는 것이다. 블록체인은 그 신뢰를 더 투명하게 구현하는 도구일 뿐이며, 프록시 패턴과 멀티시그 거버넌스, 타임락을 결합한 하이브리드 구조가 금융 도메인에서 현실적인 균형점이 될 것으로 판단된다.
